# Methodologier

## Overview

A seed insights document is the highest-leverage input you can give an AI coding agent. It encodes *how* to think about the project — design philosophy, architectural instincts, quality guardrails — before a single line of code is written. This skill builds and maintains that document across two modes:

- **`--init`** — Pre-project: interview the user, then generate the seed document
- **`--analyze`** — Mid-project: read the current codebase, extract insights, update the document

## When to Use

- User says "build my seed doc", "start methodologier", or "run methodologier --init"
- Before entering any SDD / spec-driven workflow
- Periodically during development to capture architectural evolution
- After major refactors or design pivots

## Mode 1: `--init` — Build the Seed Document

### Step 1: Interview the User

Ask these questions in **conversational batches** (not all at once). Wait for answers before proceeding.

**Batch A — Project Identity**
1. What is this project building? (one paragraph description)
2. What is the primary tech stack? (languages, frameworks, runtimes)
3. Who are the primary users/consumers of this system?

**Batch B — Quality Priorities** (ask user to rank top 3)
- Performance / low latency
- Scalability (horizontal / vertical)
- Maintainability / long-term evolvability
- Developer experience / DX
- Reliability / fault tolerance
- Security / compliance
- Time-to-market / shipping speed
- Extensibility / plugin-friendly

**Batch C — Architecture Signals**
4. Is this a greenfield project or evolving an existing codebase?
5. What known technical constraints exist? (infra, team size, budget, deadlines)
6. What are the biggest failure risks you want to guard against?
7. Any past architectural mistakes you want to explicitly avoid?

**Batch D — Development Philosophy**
8. How do you approach testing? (TDD, test-after, integration-only, etc.)
9. Preferred code review / iteration style? (tight loops, PR-based, async, etc.)
10. Any specific design philosophies you want enforced? (DDD, hexagonal, event-driven, etc.)

### Step 2: Generate the Seed Document

Write the document to `docs/seed-insights.md` (create `docs/` if absent).

Use this structure, populated from answers + derived reasoning:

```markdown
# [Project Name] — Seed Insights

> Generated by Methodologier. Update with `methodologier --analyze`.

## Engineering Philosophy

Core principles that guide every decision in this codebase.

### Non-Negotiables
- [Derived from quality priorities, constraints, failure risks]

### Design Mantras
- [SOLID / DRY / KISS / YAGNI applied specifically to this project's context]

### What We Explicitly Avoid
- [Anti-patterns, over-engineering traps, past mistakes named by user]

---

## Architecture Patterns

### Core Pattern
[Primary architectural style: layered, hexagonal, event-driven, modular monolith, etc.]

### Module Boundaries
[How to split responsibility. What belongs where. Coupling rules.]

### Data Flow
[How data moves through the system. Source of truth ownership.]

### Extension Points
[Where the system is designed to grow. Where to add, not modify.]

---

## Development Methodology

### Spec Before Code
[How to approach new features — spec/design first, then implementation]

### Testing Strategy
[Unit / integration / e2e split. What must be tested. What can be skipped.]

### Iteration Model
[How to break down work. PR size. Review cadence.]

---

## Quality Guardrails

### Performance Budget
[Latency targets, resource constraints if stated]

### Security Baseline
[Auth model, input validation policy, secrets handling]

### Complexity Ceiling
[When to split a module. When to extract. When to reject scope creep.]

---

## Project-Specific Insights

> This section grows over time via `methodologier --analyze`.

*(empty at init — populated by analysis runs)*
```

### Step 3: Confirm and Refine

After writing the document:
- Show the user a summary of the key philosophical choices made
- Ask: "Does this capture your intent? Anything to adjust or add?"
- Incorporate feedback, then finalize

## Mode 2: `--analyze` — Extract Insights from Codebase

Use this when the user calls `methodologier --analyze` during active development.

### Step 1: Codebase Reconnaissance

Read in this order:
1. `docs/seed-insights.md` (existing document — understand current baseline)
2. Project root files: `README.md`, `pyproject.toml` / `package.json` / `Cargo.toml`, config files
3. Main entry points: `main.py`, `index.ts`, `app.py`, `src/main.*`, etc.
4. Architecture-heavy directories: `src/`, `lib/`, `core/`, `domain/`, `services/`
5. Test structure: `tests/`, `__tests__/`, `spec/`

Use structural scanning (file tree + key file reads), not exhaustive line-by-line reading.

### Step 2: Extract Insights

Identify and document:

| Category | What to Look For |
|---|---|
| **Coupling patterns** | How modules import each other. Circular deps. Tight vs loose coupling. |
| **Abstraction quality** | Interface clarity. Over-abstraction. Missing abstractions. |
| **Consistency signals** | Naming conventions. Error handling patterns. Config discipline. |
| **Testing maturity** | Test coverage style. What's covered vs ignored. Test quality. |
| **Technical debt hotspots** | Duplicated logic. God objects. Mixed concerns. TODO density. |
| **Emergent patterns** | Conventions that evolved organically (good or bad). |
| **Architecture drift** | Places where current code diverges from stated principles. |

### Step 3: Update the Seed Document

Append or update the **Project-Specific Insights** section with timestamped entries:

```markdown
## Project-Specific Insights

### [YYYY-MM-DD] Analysis Run

**Confirmed patterns working well:**
- [e.g., "Service layer cleanly separates business logic from HTTP handlers"]

**Emerging conventions to reinforce:**
- [e.g., "All DB queries go through repository classes — enforce this going forward"]

**Architecture drift detected:**
- [e.g., "Auth logic scattered across 3 modules — consolidate into auth/ domain"]

**Recommended guardrails to add:**
- [e.g., "No direct DB access from route handlers — add linting rule or review note"]
```

Then offer to update the **Quality Guardrails** or **Architecture Patterns** sections if insights suggest the original document needs revision.

## Common Mistakes

| Mistake | Fix |
|---|---|
| Asking all questions in one wall of text | Batch into 3-question groups, wait for answers |
| Generic advice not tied to this project | Every principle must connect to user's specific answers |
| Skipping Batch D (philosophy) | Philosophy is what prevents architectural drift — never skip it |
| Over-indexing on one principle | Balance: DRY vs YAGNI, abstraction vs simplicity |
| `--analyze` without reading existing seed doc first | Always read existing doc before analysis to measure drift |
| Writing insights as vague observations | Make every insight actionable — what should change? |

## Seed Document Placement

Default: `docs/seed-insights.md`

Alternatives (if user has conventions):
- `.claude/seed-insights.md` — preferred when project uses CLAUDE.md already
- `ARCHITECTURE.md` — if project uses architecture docs as top-level convention

Always ask if no `docs/` directory exists: "Where should I save the seed document?"
