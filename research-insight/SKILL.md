# Research Insight Skill

产出面向技术团队内部分享的中文洞察文档。目标不是"总结"，而是让读者在 5-10 分钟内抓住一个项目/论文的核心价值、设计哲学和可借鉴之处。

## 工作流总览

```
输入材料 → Phase 1 识别与策略 → Phase 2 核心提取 → Phase 3 批判性思考 → Phase 4 有限发散 → Phase 5 结构化输出
```

以下逐阶段展开。

---

## Phase 1：材料识别与策略选择

拿到输入后，先判断材料类型。判断依据：

| 信号 | 类型 |
|---|---|
| GitHub 链接、代码仓库、软件项目名 | `codebase` — 开源项目/软件工程 |
| arXiv 链接、会议论文、方法+实验结构 | `paper` — 学术论文 |
| 标题含 "survey"/"review"/"综述"，篇幅长，大量引用分类 | `survey` — Survey/综述 |
| 来自 OpenAI/Google/Anthropic/Meta 等发布的模型报告 | `tech-report` — 大模型技术报告 |
| 以定理/证明/形式化推导为主体 | `theory` — 理论性质论文 |

判断完成后，读取对应的 reference 文件获取该类型的专属指导：

- `codebase` → 读取 `references/codebase.md`
- `paper` → 读取 `references/paper.md`
- `survey` → 读取 `references/survey.md`
- `tech-report` → 读取 `references/tech-report.md`
- `theory` → 读取 `references/theory.md`

如果用户已经在 prompt 中明确说明了类型，直接跳过判断。如果材料混合（比如一个既有论文又有代码的项目），以用户意图为主，也可以同时参考两份 reference。

---

## Phase 2：机制解析（核心阶段，应占全文 ~60% 篇幅）

这是整篇洞察最重要的阶段。读者最需要的不是"这个工作好不好"，而是**"它到底是怎么做的，为什么能 work"**。如果读者看完洞察还是说不清核心方法的运作机制，这篇洞察就失败了。

每种类型的提取重心不同，详见对应的 reference 文件。但所有类型都必须构建一条完整的**"机制解释链"**：

### 机制解释链（Mechanism Chain）

对于每一个核心贡献点，必须按以下链条组织解释，形成一个完整的理解闭环：

```
问题是什么 → 关键洞察/直觉 → 具体怎么实现 → 为什么这样做能解决问题
```

四个环节缺一不可：

1. **问题是什么**：不是泛泛的"提升性能"，而是具体的技术障碍。比如"现有 agent 框架中，长 context 下工具调用的准确率从 95% 降到 60%"。
2. **关键洞察（Insight）**：作者想到了什么别人没想到的？这通常是论文中最值得传达的部分。比如"与其让单个模型处理超长 context，不如把 context 分层、按相关性动态加载"。
3. **具体实现**：洞察如何变成可运行的方案？这里需要足够的细节让读者理解机制的运作方式——关键数据结构、算法步骤、模块交互。用 mermaid 流程图/架构图辅助解释。代码项目应贴关键代码片段（10-30 行）并附 GitHub 链接。
4. **为什么能 work**：这个方案为什么能解决上面的问题？是因为减少了计算复杂度？利用了某个数学性质？改变了信息流的拓扑？这一步是从"知道它做了什么"到"理解它为什么有效"的关键跳跃。

如果一个工作有多个贡献点，为每个核心贡献分别构建解释链，但通常只需要深入展开最重要的 1-2 个。

### 通用原则

- **抓本质而非罗列**：不要按原文章节顺序复述，而是围绕机制解释链重新组织。
- **视觉化机制**：核心机制的运作方式必须用 mermaid 图展示。这张图不是装饰，而是帮读者建立心智模型的核心工具。
- **标注来源**：引用的代码给出 GitHub 永久链接，引用的论述给出原文链接。
- **深度优先于广度**：宁可一个核心机制讲透，也不要五个特性各讲一句。

### 材料获取最佳实践

- **代码仓库**：优先 clone 到本地直接阅读源码，而非仅看 README。重点读核心模块的入口文件和关键抽象。
- **论文/报告**：如果用户提供了 PDF，直接读取。如果只给了链接，先获取全文。
- **辅助资料**：官方博客文章、作者的演讲 slides、项目的 design doc 往往比论文本身更能说清动机，值得查找。

## Phase 3：批判性思考（~30% 篇幅，服务于理解而非替代理解）

批判性分析建立在读者已经理解核心机制的基础上。如果 Phase 2 没有讲清"怎么做的"，Phase 3 的评价就是空中楼阁。

从以下维度池中，根据材料类型选取 **1-2 个**最相关的维度进行分析（不要贪多）：

| 维度 | 含义 | 适用类型 |
|---|---|---|
| **隐含假设与局限性** | 方法成立的前提条件是什么？哪些场景下会失效？作者没说的 limitation 是什么？ | 所有类型 |
| **差异化定位** | 与最相关的 2-3 个同类工作相比，本质区别在哪？是增量改进还是范式转变？ | paper, tech-report, survey |
| **工程落地距离** | 从 idea/paper 到生产环境部署还差什么？需要什么额外工程、数据、基础设施？ | paper, tech-report, codebase |
| **可迁移洞察** | 对 agentic 系统、上下文工程、模型训练、网络运维等方向有什么可借鉴的思路？ | 所有类型 |
| **架构哲学** | 核心设计决策背后的 trade-off 是什么？体现了什么工程价值观？ | codebase |
| **业界认可度** | GitHub stars、引用数、社区讨论热度、被哪些知名项目采用？ | codebase, paper, tech-report |
| **规模化特性** | 在数据量/模型规模/用户量增长时的行为变化，是否有明确的 scaling 规律？ | tech-report, theory |

每种类型的默认选取策略在对应的 reference 文件中定义。用户也可以在 prompt 中指定关注维度来覆盖默认选择。

**写作要求**：批判性分析不是吹毛求疵，而是帮读者建立判断力。每个观点都要有依据——来自论文本身的证据、与其他工作的对比、或工程常识。避免空泛的"可能有局限性"式评论。

---

## Phase 4：有限发散

**预算：每篇洞察最多 1-2 次额外搜索。**

发散搜索的目的是为批判性分析补充外部证据，而不是扩展覆盖面。触发条件：

1. Phase 3 中提出了一个判断，但缺乏足够的外部对比数据来支撑（比如"与 X 方法相比有优势"但你不确定 X 的最新进展）
2. 某个核心概念是该领域的新提法，读者可能不熟悉，需要补充 1-2 句背景
3. 需要验证业界认可度（star 数、引用数等）

**不要发散的情况**：
- 论文自身已经充分讨论了 related work
- 补充信息对核心洞察的增益很小
- 用户 prompt 中明确要求快速产出

发散搜索的结果以脚注或内联引用的形式融入正文，不单独成章。

## Phase 5：结构化输出

### Frontmatter

每篇洞察必须包含以下 frontmatter：

```yaml
---
project_name: <项目/论文名称>
project_link: <GitHub 链接或项目主页，无则填 NOT_FOUND>
paper_link: <论文链接(arXiv/DOI)，无则填 NOT_FOUND>
team: <团队/机构名>
insight_date: <YYYY-MM-DD 格式，使用当天日期>
content_status: done
---
```

### 篇幅自适应标准

| 材料复杂度 | 判断信号 | 建议篇幅 |
|---|---|---|
| 轻量 | 单一明确的贡献点，方法简洁，代码量 <5k 行 | 1000-2000 字 |
| 标准 | 2-3 个贡献点，有完整实验，代码量 5k-50k 行 | 2000-4000 字 |
| 重量 | 多个子系统/贡献，大型 survey，代码量 >50k 行 | 4000-6000 字 |

这里的"字"指正文内容，不含 mermaid 代码和表格标记。宁可精炼也不要注水——如果一个项目用 1500 字就能说清楚，不要为了凑篇幅而展开。

### 可视化要求

- **必须包含**：至少一个 mermaid 图（架构图、流程图或概念层次图，视类型而定）
- **推荐使用**：表格呈现对比信息、配置参数、实验结果等结构化数据
- **mermaid 图类型选择指南**：
  - 系统架构 → `graph TD` 或 `graph LR`
  - 时序/流程 → `sequenceDiagram` 或 `flowchart`
  - 类层次/概念关系 → `classDiagram`
  - 时间线/版本演进 → `timeline`
  - 文件目录结构 → 用代码块而非 mermaid

### 写作风格

- 语言：中文，技术术语保留英文原文（首次出现时可加中文注释）
- 语气：专业但不枯燥，像在和同事做技术分享而非写学术综述
- 结构：用清晰的标题层级组织，但标题本身要有信息量（"基于 DAG 的任务编排" 而非 "系统设计"）
- 代码引用：关键代码片段直接贴出（控制在 10-30 行），并给出 GitHub 永久链接
- 链接：所有引用的外部资源（博客、论文、代码）都附上可点击的链接

### 输出路径

用户会在 prompt 中指定输出目录（如 `insights/agent/code_agent`）。如果没有指定，询问用户。文件名使用小写英文 + 下划线，如 `deerflow_v2.md`。

## 附录：快速参考

### 完整工作流 Checklist

1. ☐ 识别材料类型，读取对应 reference 文件
2. ☐ 获取材料（clone 代码 / 获取论文全文 / 读取 PDF）
3. ☐ 构建机制解释链：问题 → 洞察 → 实现 → 为什么 work（~60% 篇幅）
4. ☐ 自检机制解释链：读者看完能否向同事复述核心方法？如果不能，需要补充细节
5. ☐ 选取 1-2 个批判性维度进行分析（~30% 篇幅）
6. ☐ 如有需要，执行 1-2 次发散搜索补充证据
7. ☐ 按 frontmatter 和格式要求组织输出
8. ☐ 自检：是否有至少一个 mermaid 图？关键引用是否都附了链接？篇幅是否匹配复杂度？

### 反模式（避免这些）

- ❌ **跳过机制直接评价**（读者还没理解"怎么做的"就被告知"好不好"——这是最常见的问题）
- ❌ **机制解释链断裂**（只说了"做了什么"但没解释"为什么能 work"，或只有直觉没有具体实现）
- ❌ 按原文章节顺序复述内容（应围绕机制解释链重新组织）
- ❌ 罗列所有功能特性不做取舍（应聚焦核心 1-2 个贡献的机制深度解析）
- ❌ 批判性分析篇幅超过机制解析（评价应服务于理解，而非喧宾夺主）
- ❌ 过度发散搜索（严守 1-2 次预算）
- ❌ 忽略可视化（再短的洞察也应有至少一张架构/概念图）
- ❌ 遗漏来源链接（每个事实性声明都应可追溯）
