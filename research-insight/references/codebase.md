# 开源项目 / 软件工程分析指南

当材料是一个 GitHub 仓库、开源工具、框架或基础设施项目时，使用本指南。

## 核心提取重心

开源项目的洞察目标是回答：**这个项目的核心机制是怎么运转的，关键设计决策背后的 why 是什么。**

### 第一步：快速建立全局认知（控制在 10-15 分钟内）

1. 读 README 和核心文档（ARCHITECTURE.md, DESIGN.md 等，如果有的话）
2. 看项目目录结构，识别核心模块和边界
3. 检查 package 依赖，理解技术栈选型
4. 如果有 CHANGELOG 或 release notes，快速浏览演进历史

### 第二步：构建机制解释链（最重要）

开源项目的"机制"体现为：**核心功能是怎么实现的**。不要停留在架构框图层面。

按 SKILL.md 中定义的机制解释链，对项目最核心的能力展开：

1. **这个项目要解决什么问题**：不是 README 里的营销语言，而是具体的技术痛点
2. **核心设计洞察**：作者采用了什么关键的设计思路来解决这个问题？这个思路与"最显而易见的做法"有什么不同？
3. **具体实现**：这是最需要深入源码的部分——
   - 核心模块的入口文件和关键抽象（接口、基类、trait/protocol）
   - 关键数据流：一个请求/任务从进入系统到产出结果的完整路径
   - 贴核心代码片段（10-30 行），附 GitHub 永久链接
   - 用 mermaid 画出核心数据流或模块交互图
4. **为什么这样设计能 work**：这个架构/实现方式为什么能有效地解决上述问题？trade-off 是什么？

### 第三步：识别关键设计决策

在理解了核心机制后，挑出 2-3 个最重要的设计决策（不是全部），每个回答：
- 选择了什么方案？
- 有哪些显而易见的替代方案没选？为什么？
- 这个决策的 trade-off 是什么？

### 第四步：技术栈速览

用表格呈现核心依赖和选型理由，篇幅要短（这是辅助信息，不是主体）。

## 输出结构模板

```markdown
# [项目名] 洞察

## 一句话定位
<!-- 用一句话说清楚这个项目是什么、解决什么问题、面向谁 -->

## 架构全景
<!-- mermaid 架构图 + 文字说明 -->
<!-- 重点：模块划分的逻辑是什么，数据怎么流动 -->

## 核心机制详解
<!-- 这是全文最重要的部分，应占最大篇幅 -->
<!-- 按机制解释链展开：问题 → 设计洞察 → 具体实现 → 为什么 work -->
<!-- 贴关键代码片段（10-30行），附 GitHub 链接 -->
<!-- mermaid 数据流图展示一个请求的完整生命周期 -->

## 关键设计决策
<!-- 2-3 个决策：选了什么 → 为什么 → trade-off -->

## 技术栈与依赖
<!-- 表格，简洁 -->

## 批判性分析
<!-- 1-2 个维度 -->

## 关键收获
<!-- 2-3 条最值得记住的 takeaway -->

## 参考资源
<!-- 本次洞察引用的所有链接 -->
```

## 默认批判性维度

对开源项目，默认选取以下 **2 个**维度：

1. **架构哲学**：核心设计决策体现了什么工程价值观？可扩展性 vs 简洁性？灵活性 vs 性能？
2. **业界认可度**：Star 数、contributor 数量、issue 活跃度、被谁在用？

如果项目与 agentic 系统、上下文工程、模型训练或网络运维相关，额外选取「可迁移洞察」维度。

## 特别注意

- 判断洞察质量的第一标准：读者看完能否说清"一个请求从进入到产出经历了哪些步骤"
- 文件目录结构用代码块呈现，不用 mermaid
- 对于大型 monorepo，聚焦核心子包而非试图覆盖全部
- 如果项目有配套论文，交叉参照论文理解设计动机，但洞察仍以代码实现为主视角
- "核心机制详解"应占全文约 60% 篇幅
